# ADR-009: 2초 블록 체인에서의 Gateway 체인 읽기 — "머리 고정" 대신 "읽은 블록이 그대로인가"

- Status: Accepted
- Scope: `packages/contracts-sdk/src/v2-chain-reader.mjs` (Gateway 직접 RPC 판정, `/ledger` 화면), `apps/gateway/src/admission-fallback.mjs` 시간 예산
- Date: 2026-10-26
- Related: [ADR-006](adr-006-gateway-recheck-policy.md), [ADR-008](adr-008-independent-evidence-and-dissent.md), 3차 멘토링 요구 ①(Base Sepolia에서 두 회사 차단)

## Context

- 기존 리더는 한 번 읽는 동안 최신 블록(`latest`)이 조금이라도 바뀌면 그 판정을 버렸다. 허용(VERIFIED)이면 한 번 다시 읽고, 다시 바뀌면 판정 불가로 처리해 차단했다. 거부 쪽 판정은 바뀌면 바로 차단했다.
- Base Sepolia는 2초마다 블록이 생긴다. 한국에서 공개 RPC(`https://sepolia.base.org`)로 한 번 읽는 데 1~2.5초가 걸리고, RPC 서버 여러 대가 서로 다른 최신 블록을 돌려준다.
- 2026-10-26 실측(V3 배포본, 정상 1.0.0과 폐기 1.0.1)에서는 두 버전 모두 매번 `STATUS_UNAVAILABLE`로 차단됐다.
  - 폐기된 1.0.1은 결과로는 맞게 막혔지만, 이유가 "폐기"가 아니라 "판정 불가"로 남았다.
  - **승인된 1.0.0도 막혔다.** 그래서 "B사는 체인 기록만 보고 바로 쓴다"는 장면을 실제 체인에서 보일 수 없었다.
- 기존 규칙이 막던 위험은 "읽는 1~2초 사이 새 블록에 폐기가 들어온 경우"다. 그런데 허용 판정은 원래부터 1블록 뒤 확정 블록(confirmations 2)에서 읽고, 허용 결과는 최대 30초 캐시한다. 그래서 1~2초를 지키려는 규칙이 가용성을 통째로 잃게 만들었다.

## Decision

1. **읽은 블록이 그대로인지 확인한다.** 읽기를 마친 뒤 이번에 쓴 머리 블록과 확정 블록을 **번호로**, 캐시 없이 다시 읽는다. 해시가 다르면 재정렬(reorg)로 보고 차단한다. 최신 블록이 같은 높이인데 해시가 다른 경우도 재정렬로 본다.
2. **머리가 앞으로 자라는 것은 허용한다.** 최신 블록이 이번 읽기의 머리보다 최대 `MAX_HEAD_ADVANCE = 3`블록(Base 기준 약 6초)까지 앞서 있어도 판정을 유지한다. 그보다 많이 앞서 있거나, RPC 서버가 이번 머리 블록을 아직 모르면(빈 응답), 허용 판정에 한해 전체를 한 번 다시 읽는다. 두 번째도 같으면 차단한다.
3. **차단 우선은 그대로 지킨다.** 허용하려면 RPC의 최신 상태(`getDecision` at `latest`)도 VERIFIED여야 한다. 아니면 전체를 한 번 다시 읽고, 그 새 머리에서 나온 거부 판정을 그대로 돌려준다. 그래서 읽는 사이 새 블록에 들어온 폐기도 놓치지 않는다.
   - 최신 상태에서 한 번이라도 거부를 봤다면, 그 사실은 읽기 전체에 남는다(`newerDenialSeen`). 다시 읽은 뷰가 VERIFIED를 줘도, 다른 RPC로 넘어가도 허용하지 않는다.
   - 최신 블록 번호가 이번 머리보다 낮게 나오면(뒤처진 서버) 허용 판정을 한 번 다시 읽게 한다.
4. **거부 판정은 재정렬 증거가 없으면 그대로 돌려준다.** 느린 RPC 서버 때문에 확인이 덜 끝나도 "폐기"를 "판정 불가"로 바꾸지 않는다. 잘못된 거부는 차단 쪽으로 실패하지만, 잘못된 허용은 그렇지 않기 때문이다.
5. **Gateway 직접 RPC 시간 예산 상한을 1500ms에서 3000ms로 올린다.** 기본값 1500ms는 그대로 둔다.

## 바뀌지 않는 것

- 확정 블록 기준 허용, 현재·확정 판정의 같은 증명 요구, 신원(digest 4종) 재확인, 검증자 집합 버전 고정
- 머리 블록 시각 30초 신선도, 허용 결과 30초 상한, 전 과정 단일 마감 시간
- 오류·불일치·시간 초과는 모두 차단(fail-closed). 다른 RPC로 돌아가 허용을 다시 노리지 않음

## 결과

- 실측(2026-10-26, `https://sepolia.base.org`, 3회 반복): 정상 1.0.0은 `VERIFIED`(1.0~2.5초), 폐기 1.0.1은 `REVOKED`(약 1.1초). 공개 RPC `base-sepolia-rpc.publicnode.com`은 여전히 실패해서 기본값으로 쓰지 않는다.
- 테스트: `apps/gateway/test/v2-chain-reader.test.mjs`의 이전 규칙 테스트("연속으로 자라는 머리는 거부")를 새 규칙으로 바꿨다. 새 테스트가 확인하는 것:
  - 자라는 머리, 연속 성장, 느린 서버에서는 허용한다.
  - 새 블록의 폐기, 머리·확정 블록·최신 블록의 재정렬, 폭주하는 머리에서는 차단한다.
  - 느린 서버 + 폐기 상태면 "폐기"를 돌려준다.

## 내부 리뷰 (2026-10-26)

공격자 관점의 별도 리뷰에서 "잘못 허용" 경로 2개(High)가 재현됐고, 둘 다 고친 뒤 회귀 테스트로 고정했다(`a newer denial seen once is never forgotten…`).

- **F1.** 최신 상태가 REVOKED라서 다시 읽었는데, 다시 읽은 뷰가 뒤처진 서버에서 VERIFIED를 받으면 그대로 허용했다.
- **F2.** 최신 상태 REVOKED를 본 뒤 첫 RPC가 시간 초과되면, 두 번째 RPC로 넘어가 허용했다.
- **원인과 수정:** 거부를 봤다는 기록이 다시 읽을 때와 RPC를 바꿀 때 초기화됐다. 이 기록을 읽기 전체 단위로 유지하도록 고쳤다.

## 받아들인 위험

- 허용 판정의 근거가 최신 상태보다 최대 몇 초 늦을 수 있다. 다만 최신 상태 확인(결정 3)이 폐기·격리를 다시 걸러 낸다. 그래도 그 확인 직후 생긴 블록의 폐기는 다음 호출 확인 때까지 반영되지 않는다. 이것은 기존 30초 허용 캐시와 같은 종류의 한계다.
- 최신 상태 확인(`latest`)과 최신 블록 확인은 서로 다른 요청이라 같은 블록에 묶이지 않는다. 뒤처진 서버의 오래된 VERIFIED를 최신으로 볼 수 있다. 정직하게 뒤처진 응답과 구별할 방법이 없어서, 블록 번호 하한 확인과 다음 호출 때의 재확인으로 범위를 줄인다(리뷰 F3, 재현 안 됨).
- RPC 서버 하나가 거짓 데이터를 주면 여전히 속을 수 있다. 이 위험은 서로 다른 운영자의 RPC를 여러 개 지정해서 줄인다. 이전과 같다.

# ADR-003: 검증자는 MCP를 쓰는 회사들의 컨소시엄이다

- Status: Accepted
- Scope: 캡스톤 최종 데모와 운영 설계(검증자 구성·참여 동기·독립성)
- Date: 2026-10-11
- Related: 1차 멘토링(2026-10) M5, M6, M7, M8

## Decision

검증자는 **MCP 도구를 실제로 업무에 쓰는 회사들의 보안팀**이 맡는다. 한 줄로 줄이면 "쓰는 회사가 곧 검증자"다.

| 질문 | 결정 |
|---|---|
| 누가 검증하나 | MCP를 쓰는 기업 보안팀들의 컨소시엄. 각 회사가 자기 검증자 키와 검사 환경을 운영한다 |
| 왜 참여하나 | **기여해야 쓸 수 있다.** 참여사만 조기 경보와 판정 근거 전체(보고서·증거 원문)를 받는다 |
| 누가 비용을 내나 | 참여사가 검사 비용(검사 환경·서명 운영)을 나눠 진다. 수수료 모델은 나중 확장이다. 체인 거래 gas는 현재 운영사 relayer가 대신 낸다. 컨소시엄 안의 gas 분담 방식은 미정이다([4회차 준비 항목](mentoring-2026-10-response.md#4회차-준비)) |
| 얼마나 독립적인가 | 각 참여사가 자기 AI 모델·검사 환경을 쓸 수 있다. 같은 검사 코드를 쓰면 함께 틀릴 위험이 남는다는 점을 명시한다 |
| 데모에서는 | **팀이 검증자 키 3개를 직접 운영한다.** 이 사실을 발표와 화면에 표시한다 |

보상을 나중에 도입할 때의 원칙:

- **서명 1건당 보상은 하지 않는다.** 서명 수에 돈을 주면 대충 서명할 이유가 생긴다.
- 보상·벌점은 **다시 확인할 수 있는 증거**에만 연결한다. 현재 컨트랙트도 검증자 1명의 긴급 격리를 결정적 사유 3종(`CANARY_EXFILTRATION`, `HOST_ESCAPE_ATTEMPT`, `DIGEST_MISMATCH`)에만 허용한다.
- 체인에는 증거의 해시만 있으므로, 누구나 재현할 수 있는 증거 형식과 이의제기 절차가 먼저 필요하다. 둘 다 로드맵이다.

## Reason

- 블록체인이 의미 있으려면 (1) 참여자끼리 서로 믿지 못하고, (2) 중립적인 운영자가 없고, (3) 참여 비용을 낼 이유가 있어야 한다. 기존 설계는 (1)(2)만 가정했고 (3)이 비어 있었다. 검증자가 없으면 Trust Plane 자체가 없으므로, 이것은 "나중 문제"가 아니다.
- 악성 업데이트로 가장 크게 잃는 쪽은 그 도구를 쓰는 회사다. 2025년 9월 npm `postmark-mcp` 사례처럼, 업데이트 하나로 보내는 메일이 몰래 외부로 복사될 수 있다. 각 회사는 이미 도입하는 도구를 따로 검토하고 있으므로, 검사를 나눠 맡고 결과를 공유하는 편이 각자 하는 것보다 싸다. 다만 검증자 3명·2-of-3에서는 릴리스마다 최소 2번의 검사가 필요하므로, 비용 절감은 세 회사가 각자 검사하는 경우 대비 최대 약 1/3이다. 주된 이익은 독립된 두 번째 판정과 조기 경보 공유다.
- 보안 업계에는 "기여한 쪽만 결과 전체를 받는" 공유 모델 선례(예: VirusTotal의 엔진 제공사 연동 조건)가 있다.
- 주의: 체인 상태(VERIFIED/REVOKED)는 공개 체인에 있으므로 누구나 읽을 수 있다. 참여 혜택은 상태 자체가 아니라 **판정 근거 원문, 조기 경보, 정책·검증자 교체 결정 참여권**에 둔다.

## Alternatives considered

| 대안 | 채택하지 않은 이유 |
|---|---|
| 운영사(우리 팀)가 검증자 3개를 계속 운영 | 한 주체가 3개를 모두 운영하면 "서명 3개를 가진 중앙 DB"와 다르지 않다. 데모에서만 쓴다 |
| MCP 게시자(개발사)가 스스로 검증 | 검사 대상이 판정자가 되는 이해충돌 |
| 서명 건수당 보상(토큰 등) | 증거 품질과 무관하게 서명 수를 늘릴 유인 |
| 누구나 참여하는 공개 검증자 | 신원 위조(Sybil), 증거 원문 기밀성, 현재 3명 고정 컨트랙트와 맞지 않음. MVP 범위 밖 |
| 외부 감사기관에 유료 위탁 | 업데이트마다 다시 검사하는 속도·비용을 맞추기 어렵고, 결국 단일 운영자 구조로 돌아간다 |
| 평판·홍보(악성 업데이트를 잡아낸 공개 기록)만으로 참여 유도 | 검사 비용을 지속적으로 낼 이유로는 약하다. 보조 동기로 로드맵에 둔다 |

## Consequences

- 데모가 증명하는 것은 **규칙 집행과 Gateway 차단의 연결**이지, 조직적으로 독립된 검증자가 아니다. 발표에서 그대로 말한다.
- 장면 하네스의 검증자는 운영사 API가 준 서명 템플릿(`/v1/scans/:id/attestation`)에 그대로 서명하며 독립 재검사(`prepared-verification`)를 거치지 않는다. 장면 결과 JSON도 이를 `environment.validators: SINGLE_INSTITUTION_DEMO`, `environment.validatorVerification: SIGNS_OPERATOR_TEMPLATE_NO_INDEPENDENT_RESCAN`으로 표시한다. 따라서 CAP2-202(독립 검증)의 증거가 아니다. 컨소시엄 운영에서 검증자가 운영사 템플릿에 그대로 서명하면 운영사 장악이 투표까지 번지므로, 검증자는 운영사 템플릿이 아니라 자체 재검사 결과에 서명해야 한다.
- 현재 V2 컨트랙트는 검증자 **정확히 3명, 정족수 2명** 고정이다. 참여사가 늘어나면 새 컨트랙트 버전이 필요하다(V2는 업그레이드 불가).
- 참여사 가입·탈퇴는 검증자 교체(rotation, 1일 지연)로 처리한다. 누가 교체를 결정하는지는 [ADR-007](adr-007-registry-owner-governance.md)에서 다룬다.
- **구현되지 않은 것:** 참여사 전용 보고서 접근 통제, 조기 경보 채널, 수수료 정산, 증거 재현 형식, 이의제기 절차.
- 함께 틀릴 위험: 검증자별 AI 설정은 이미 따로 줄 수 있지만, 정적 규칙과 sandbox 코드는 공유한다. 맹점이 같으면 3명이 함께 틀린다. 완화 방향은 참여사별 다른 모델과 참여사 고유 규칙 추가(로드맵)이다. 평가에서는 정적 규칙·AI·sandbox가 각각 무엇을 잡았는지 따로 보고한다([ADR-002](adr-002-ai-chain-boundary.md)와 같은 원칙).

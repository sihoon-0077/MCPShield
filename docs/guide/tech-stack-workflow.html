FROM CONCEPT TO WORKFLOW

AI가 도구를 쓰기까지,
어디서 무엇을 확인할까?

MCPShield는 AI가 사용하는 외부 도구를 검사하고,
검증된 버전만 실행하도록 통제하는 시스템입니다.
기술 이름을 실제 역할과 연결해서 읽어보세요.

흐름 따라가기 ↗기술별 역할 보기

이 상황을 떠올리면 쉽습니다

“오늘 받은 메일을 요약해줘.”
AI 에이전트→MCPShield
실행 허가 확인→메일 MCP

메일을 읽는 것은 MCP 도구.
그 버전을 실행해도 되는지 확인하고 막는 것은 MCPShield.

학습용 · 2026-09-19 기준버튼은 설명만 바꿉니다. 실제 스캔·AI 호출·체인 거래를 수행하지 않습니다. 로컬 master/main · 970cc67과 인수인계 문서를 기준으로 작성했습니다. ‘구현됨’은 코드가 있다는 뜻이며, 실제 고객 운영이나 최신 공개 배포 완료를 뜻하지 않습니다. 별도 브랜치에서 진행 중인 종합 health는 아직 통합 완료로 계산하지 않습니다.

01 / SYSTEM MAP

화면 뒤에는 이런 팀이 있습니다.

상자를 누르면 그 구성요소가 받는 정보, 하는 일,
다음 단계로 넘기는 결과를 볼 수 있습니다.

등록·검사 요청이 들어가는 길

Worker가 아래 검사를 실행합니다 ↓

검사 근거가 승인 기록으로 바뀌는 길

결과가 돌아오는 길: 체인 이벤트 → Indexer → DB / API → 화면과 Gateway의 상태 조회

등록·변경할 때

무거운 검사는 미리 합니다.

도구 등록 → 작업 큐 → 검사 → 검증자 → 체인

새 버전이나 정책 변경을 검사합니다. 시간이 걸리는 일은 Worker가 처리하고 웹은 진행 상황을 조회합니다.

실제로 사용할 때

호출 직전에 허가를 확인합니다.

AI 요청 → Gateway → 승인 확인 → MCP 실행 → 결과

Gateway는 정확한 버전·정책·만료·폐기 상태를 확인합니다. 이후 도구 호출도 다시 확인하며, 매번 전체 스캔을 돌리지는 않습니다.

02 / FOLLOW THE REQUEST

요청 하나를 끝까지 따라가 보세요.

상황을 고른 뒤 ‘다음 단계’를 누르세요.
검사 결과와 실행 허가는 어떻게 다른지 보입니다.

mail-mcp를 사용하는 합성 메일 시나리오설명용 시뮬레이션

    인쇄용 요약: 정상: 등록 → 큐 → 검사 PASS → 2인 검증 → 체인 VERIFIED → 상태 동기화 → Gateway ALLOW → 결과. 악성: 유출 증거 → 2인 FAIL → REVOKED → 실행 전 BLOCK. 판단 보류: ABSTAIN → 승인 없음 → BLOCK. 조회 장애(strict, 대체 조회도 실패): 안전 확인 불가 → BLOCK, 악성 판정과 구분.

    실제 경계: 개발용 지갑의 2-of-3는 서로 다른 기관의 검증을 뜻하지 않습니다. 최신 OCI 통합 검사와 외부 AI·테스트넷 검증은 인수인계 시점에 미완료입니다.

    03 / THE STACK, IN PLAIN WORDS

    기술 이름을 역할로 번역하면.

    ‘언어’, ‘서버’, ‘저장소’, ‘실행 환경’은 서로 다른 종류입니다. 각 기술이 맡은 한 가지 역할부터 보세요.

    FRONTEND · 사용자 화면

    React + Next.js

    React는 버튼·표 같은 화면 부품을 만듭니다. Next.js는 페이지 주소와 서버 측 처리를 연결하는 웹 프레임워크입니다.

    여기서는: 검사 요청 화면, 결과 대시보드, 운영 콘솔과 API 중계.
    구현됨 · apps/dashboard
    LANGUAGE & RUNTIME · 작성과 실행

    TypeScript + Node.js

    TypeScript는 개발 중 데이터 타입 실수를 줄이는 언어입니다. Node.js는 서버에서 JavaScript를 실행하는 환경입니다.

    여기서는: API·Worker·검증자 코드를 실행. 스캐너와 Gateway에는 JavaScript도 사용.
    구현됨 · 서버 공통
    API · 요청 접수 창구

    Fastify + 입력 검증

    Fastify가 HTTP 요청을 받고 처리 함수를 연결합니다. JSON Schema/Ajv와 검증 코드가 입력 형태를 검사합니다. 타입만으로 외부 입력이 검증되지는 않습니다.

    여기서는: 토큰·조직·권한 확인 → 등록/검사/승인 API 처리.
    구현됨 · apps/api
    DATABASE · 업무 기록

    SQLite / PostgreSQL

    SQLite는 로컬 파일에 데이터를 저장합니다. PostgreSQL은 여러 프로세스가 함께 사용하는 서버형 DB입니다. 실행 구성에 따라 선택합니다.

    여기서는: 릴리스, 검사 작업, 정책, 처리 이력 저장. 확장 /v1은 PostgreSQL adapter 제공.
    구현됨 · 운영 검증 별도
    ASYNC JOB · 오래 걸리는 일

    SQL Queue + Worker

    큐는 할 일 목록, Worker는 그 일을 가져가는 작업자입니다. 임시 점유권(lease)과 재시도 횟수를 DB에 남깁니다.

    여기서는: 검사 요청에 작업 ID 응답 → 별도 Worker가 처리 → 결과 조회.
    구현됨 · 별도 RabbitMQ 없음
    ISOLATION · 제한된 실험실

    Docker Sandbox

    후보 도구를 제한된 컨테이너에서 실행합니다. 파일·네트워크·CPU·메모리를 제한하고 행동을 관찰합니다. 컨테이너 자체가 안전성 보증은 아닙니다.

    여기서는: 가짜 비밀값을 읽거나 허용하지 않은 곳으로 보내는지 검사.
    구현됨 · 최신 OCI 통합 미완료
    ANALYSIS · 코드와 행동 읽기

    정적 규칙 + AI + Trivy

    규칙은 알려진 위험 패턴, AI는 설명과 행동의 의미, Trivy는 패키지 취약점·구성 정보를 다룹니다. 서로 다른 근거를 결합합니다.

    여기서는: ‘메일 조회’ 설명에 숨은 외부 전송 지시와 실제 관찰 결과 비교.
    외부 AI 품질 검증 남음
    TRUST · 판정의 서명과 기록

    Solidity + EVM + ethers

    Solidity는 컨트랙트 작성 언어, EVM은 실행 환경, ethers는 서버와 체인을 잇는 라이브러리입니다. EIP-712는 구조화된 판정에 서명하는 규격입니다.

    여기서는: 승인된 검증자·서명·정족수를 확인하고 릴리스 상태 기록.
    로컬 EVM 검증 · 테스트넷 남음
    EXECUTION · AI와 도구 연결

    MCP SDK + Gateway

    MCP는 AI와 도구가 목록·호출·결과를 주고받는 규약입니다. Gateway는 그 사이에서 실행 허가를 확인하는 프로그램입니다.

    여기서는: stdio/HTTP MCP 통신, 정확한 버전 확인, 실행·호출 전 차단.
    구현됨 · 지원 프로필 제한
    RECOVERY · 기록을 맞추는 일

    Outbox + Indexer

    Outbox는 체인에 보낼 일을 먼저 저장합니다. Indexer는 체인 이벤트를 읽어 DB에 반영합니다. 장애나 체인 재편성 뒤 상태를 다시 맞춥니다.

    여기서는: 전송 결과가 불확실해도 보관된 거래를 확인·복구.
    구현됨 · DB/체인 동시 완료 아님
    OBSERVABILITY · 어디서 느려졌나

    OTel + Prometheus + Grafana

    OpenTelemetry는 추적·지표 수집을 돕고, Prometheus는 수치 지표를 저장·조회하며, Grafana는 화면으로 보여줍니다.

    여기서는: 검사 시간, 실행 허가 지연, 오류 수를 보고 trace ID로 단계 연결.
    구성 있음 · 실제 알림 연결 남음
    DELIVERY · 검사하고 실행 환경 배포

    GitHub Actions + Compose

    Actions는 코드 변경 시 테스트·빌드·보안 검사를 자동 실행합니다. Compose는 관련 컨테이너를 함께 구성합니다. Railway에는 기존 웹 데모가 배포돼 있습니다.

    여기서는: push/PR 검사. 사용자의 MCP 등록은 제품의 검사 큐에서 처리.
    최신 개발본 배포와 구분
    DATABASE

    DB에 남는 것

    등록 정보, 검사 작업, 정책, 처리 상태, 감사 이벤트. 화면에서 빠르게 검색할 업무 기록입니다.

    PRIVATE STORAGE

    비공개 저장소에 남는 것

    암호화한 상세 검사 증거. 로컬 저장과 S3 adapter가 있고 실제 클라우드 운영 검증은 별도입니다.

    BLOCKCHAIN

    체인에 남는 것

    릴리스 식별 정보, 정책·증거의 해시, 판정·상태 등 최소 정보. 원본 메일·비밀키·검사 원문을 올리지 않습니다.

    블록체인의 역할은 여러 참여자가 판정·폐기 기록을 확인하는 공통 기준입니다. 악성 행동을 발견하는 일은 검사기가 하고, 실행을 막는 일은 Gateway가 합니다.

    04 / WHEN THE SYSTEM GROWS

    Nginx·Redis·Kafka·RabbitMQ는?

    모두 ‘좋은 기술’이지만 필요한 역할과 시점이 다릅니다.
    현재 시스템에 전부 설치돼 있는 것은 아닙니다.

    기술 · 쉬운 비유들어오면 맡을 일현재 방식검토할 때
    Nginx

    정문과 안내 데스크

    		한 주소의 요청을 웹·API·Gateway로 분배. HTTPS와 프록시 설정 관리.Railway HTTPS + 앱 라우팅직접 서버를 운영하거나 경로·타임아웃·스트리밍 설정을 직접 관리할 때.
    Redis

    여러 서버의 공용 메모장

    		서버 전체 호출 횟수와 짧은 캐시 공유.프로세스별 제한 + Gateway 서명 캐시API 서버 여러 대가 같은 호출 제한·임시 상태를 공유해야 할 때.
    RabbitMQ

    작업 배달 센터

    		검사 작업 전달·처리 확인·재전달. 재시도/DLQ 정책을 함께 구성.DB 기반 작업 큐 + Worker큐가 DB의 병목이 되거나 작업 종류별 분배가 복잡해질 때.
    Kafka

    다시 읽을 수 있는 이벤트 기록

    		검사·폐기 이벤트를 분석·알림·감사 서비스가 각각 소비.DB 이벤트 + Indexer + 화면 알림독립 서비스가 같은 이벤트를 계속 읽고 과거부터 재처리해야 할 때.

    큐를 바꿔도, 검사가 저절로 빨라지진 않습니다.

    병목이 AI 호출이나 격리 실행 시간이라면 Worker 자원과 검사 방식부터 봐야 합니다. RabbitMQ도 중복 전달이 가능하므로 멱등성은 유지합니다. Kafka의 순서 보장은 같은 파티션 안에서입니다.

    보안 판정을 캐시할 때는 더 조심합니다.

    Redis에 오래된 ALLOW가 남으면 폐기를 놓칠 수 있습니다. 저장소를 바꿔도 서명·대상·정책·만료 확인과 폐기 규칙은 유지해야 합니다. 캐시는 현재 상태 확인을 무조건 대신하지 않습니다.

    06 / KEEP THIS DICTIONARY OPEN

    헷갈리는 용어, 한 문장씩.

    용어를 누르면 MCPShield에서의 의미가 펼쳐집니다.

    MCP AI와 도구의 대화 규칙

    도구 목록을 알려주고, 도구를 호출하고, 결과를 돌려주는 통신 규약입니다. MCP 자체가 도구의 안전성을 보증하지는 않습니다.

    API / BFF 기능 창구 / 화면용 중계

    API는 프로그램이 기능을 요청하는 창구입니다. BFF는 브라우저와 백엔드 사이에서 화면에 필요한 요청을 중계합니다. 이 프로젝트의 BFF는 사용자의 권한을 유지하고 허용한 경로만 전달합니다.

    Release / Digest 정확한 배포본 / 파일 지문

    릴리스는 특정 배포본입니다. digest는 그 파일 내용의 해시입니다. 이름·버전 표시가 같아도 내용이 달라지면 지문이 달라지므로 승인된 바이트와 비교합니다.

    Tool surface AI에게 보이는 도구 설명서

    도구 이름, 설명, 입력 구조 등의 목록입니다. 도구 코드뿐 아니라 AI의 행동을 유도하는 이 설명도 변경 여부를 확인합니다.

    Tenant / Role 어느 조직 / 어떤 권한

    tenant는 조직별 데이터 경계, role은 그 안에서 할 수 있는 일입니다. reader는 조회, operator는 검사·증거 등 운영, admin은 관리 권한을 갖습니다. 검증자 서명 키는 별도입니다.

    Idempotency 같은 요청의 중복 반영 방지

    응답을 못 받아 재전송해도 같은 작업이 두 번 생기지 않게 합니다. 동일 요청 키와 내용을 묶어 저장하며, 같은 키로 다른 내용을 보내면 충돌로 거부합니다.

    Lease / Retry / DLQ 점유권 / 재시도 / 실패 보관

    lease는 Worker가 작업을 처리할 임시 권리입니다. 일시 장애는 간격을 두고 제한 횟수만 재시도합니다. 한도를 넘거나 재시도 불가이면 DEAD_LETTER로 보관하고 원인을 확인합니다.

    Sandbox / Canary 실험실 / 가짜 비밀값

    샌드박스는 실행 권한을 제한한 공간입니다. canary는 일부러 넣은 합성 비밀값으로, 외부에서 관찰되면 데이터 유출의 근거가 됩니다. 실제 고객 비밀을 테스트에 사용하지 않습니다.

    Merkle root 여러 증거의 대표 지문

    여러 증거 파일의 해시를 묶은 최상위 해시입니다. 증거가 바뀌었는지 검증하는 데 쓰며, 지문이 일치한다고 증거 내용이나 도구가 자동으로 안전해지는 것은 아닙니다.

    2-of-3 / EIP-712 판정 정족수 / 구조화 서명

    등록된 세 검증자 중 필요한 두 명의 판정을 확인합니다. EIP-712 서명은 어떤 릴리스·정책·근거·유효기간에 동의했는지 묶습니다. 같은 운영자가 가진 지갑 세 개는 독립 기관 세 곳과 다릅니다.

    Indexer / Reorg 체인 기록 읽기 / 체인 재편성

    Indexer는 체인 이벤트를 DB에 반영합니다. reorg로 과거에 보였던 블록이 최종 경로에서 빠지면 확정 판단과 DB 기록을 재확인하고 복구해야 합니다.

    Admission / Fail closed 실행 허가 / 확인 실패 시 차단

    admission은 이 요청에서 이 도구를 실행해도 되는지 판단하는 절차입니다. strict 모드에서 필요한 승인을 확인할 수 없으면 차단합니다. 서버 장애로 막힌 경우와 악성으로 폐기된 경우는 다릅니다.

    PASS / VERIFIED / ALLOW 검사 / 릴리스 상태 / 현재 요청

    PASS는 검사 판정, VERIFIED는 검증 절차를 거친 릴리스 상태, ALLOW는 현재 실행 요청의 허가입니다. VERIFIED여도 파일 불일치·정책·만료 문제로 BLOCK될 수 있습니다.

    ABSTAIN / QUARANTINED / REVOKED 보류 / 임시 격리 / 폐기

    ABSTAIN은 판정할 근거가 부족한 검사 결과, QUARANTINED는 임시 격리 상태, REVOKED는 폐기 상태입니다. 이의제기를 종결해도 폐기가 취소되거나 실행이 승인되지는 않습니다.

    Trace / Metric / Log 한 요청의 길 / 수치 / 사건 기록

    trace는 요청이 지나온 단계, metric은 지연·오류 수 같은 수치, log는 발생 사건의 기록입니다. 현재 관측 구성과 실제 장기 보관·사람에게 알림 전달은 별개입니다.

    CI/CD / 제품 검사 큐 우리 코드 검증 / 사용자 도구 검사

    CI는 개발자가 코드를 push/PR할 때 실행하는 자동 검사입니다. CD는 배포 자동화입니다. 사용자가 MCP를 등록해서 받는 검사는 제품의 API·Worker가 수행하며 GitHub CI와 다릅니다.

    07 / THREE DIFFERENT TRIGGERS

    ‘자동으로 한다’는 같아도, 시작점은 다릅니다.

    사용자가 늘어난다고 GitHub CI가 호출마다 실행되는 구조가 아닙니다.

    개발자가 우리 코드를 고쳤을 때

    CI · 코드 자동 검사

    코드 push / PR → 테스트·빌드 → 통과 또는 실패

    검사 대상은 MCPShield 자체 코드입니다. 새 변경 때문에 기존 차단 기능이나 화면이 망가지지 않았는지 확인합니다. CD는 검증한 버전을 배포하는 별도 단계입니다.

    GitHub Actions 구성 있음
    사용자가 MCP 도구를 등록했을 때

    제품의 검사 큐

    웹·API 등록 → SQL Queue → Worker → 보안 검사

    검사 대상은 사용자가 등록한 도구의 특정 버전입니다. 요청이 많아지면 대기 작업·처리 시간·Worker 자원을 살펴봅니다. GitHub CI 실행 횟수와는 다른 문제입니다.

    API·SQL 큐·Worker 구현됨
    서비스가 계속 정상인지 확인할 때

    운영 감시 · 장애 알림

    주기적 점검·지표 수집 → 장애 감지 → 담당자 알림

    검사 대상은 실행 중인 서비스의 상태입니다. 코드가 바뀌지 않아도 DB·RPC·검사 Worker는 멈출 수 있습니다. 알림 수신자를 연결하고 실제 장애를 넣어 전달까지 확인해야 합니다.

    관측 구성 있음 · 종합 상태 통합·실제 알림 남음

    ‘서버 켜짐’과 ‘업무 가능’도 다릅니다.

    Liveness는 서버가 응답하는지, readiness는 필요한 DB·체인·검사기가 준비됐는지 확인합니다. 상태가 정상이어도 특정 도구의 안전 승인은 별도입니다. 기존 /health 응답을 전체 기능 정상으로 읽지 마세요.

    문제가 생기면 어디서 볼까요?

    1. /console: 검사 상태·실패 이유·릴리스 이력
    2. API·Worker·Gateway 로그: 요청의 trace ID로 연결
    3. 관측 구성 실행 시 Grafana: 오류 수·지연 시간
